\chapter{Release 2: Payments, Intelligence, Community, and Finalization}

\clearpage
\section*{Introduction}

The second release of ForsaDrive picks up where the first one left off. By the end of chapter~4 the platform supported the core booking loop, but a number of features that turn a working prototype into a usable product were still missing: a wallet that consolidates the financial activity of a user, the analytics that drivers need to understand their performance, the community features that make a carpooling application attractive to return to, and the multilingual interface that the Tunisian context requires. Sprint~3 was dedicated to the \textit{Payments and Intelligence} side of this work, and Sprint~4 covered the \textit{Community and Finalization} side, including the testing strategy and the deployment of the application. This chapter follows the same structure as the previous one --- backlog, detailed conception when relevant, realization, sprint review --- and closes with the testing approach that was applied to the entire platform and a brief description of the deployment.

\section{Sprint 3 --- Payments and Intelligence}

\subsection{Sprint Goal and Backlog}

The goal of Sprint~3 was twofold. On the one hand, the wallet had to be turned from a hidden internal mechanism into a screen that users can actually consult, with a clear distinction between the available balance, the pending amounts, and the history of operations. On the other hand, the platform needed enough intelligence to remain useful when the catalog of rides grows: a search that would return the result list in chronological order would quickly lose its relevance once the database contains more than a handful of trips. \subsection{Detailed Conception}

The most sensitive piece of this sprint is the price computation pipeline, since several rules apply on top of each other: the base price per seat, the seat count, the student discount, and an optional promo code. The order in which these reductions are applied directly affects the amount paid and refunded, which made it worth fixing on paper before any line of code was written. The team chose the following order, which was reviewed and accepted by the supervising engineer:

\begin{enumerate}[noitemsep]
    \item Start from $\textit{base price} = \textit{seat price} \times \textit{seat count}$.
    \item If the passenger is a verified student, apply the fifty-percent student discount.
    \item If a valid promo code is provided, apply its percentage on the result of step~2.
    \item Compute the prepayment as fifty percent of the resulting amount.
    \item Store on the booking row the original price, the applied discounts, the total to pay, the prepayment, and the remaining amount to settle in cash.
\end{enumerate}

The reliability score of a driver is recomputed every time a trip is marked as completed. The formula combines the average rating, the completion rate, and the cancellation rate, each weighted by a coefficient that was tuned on a small set of synthetic histories. The exact weights are not detailed here as they are an implementation choice rather than a structural one, but the principle is the same throughout: the reliability score is a single number between zero and one hundred that summarizes how trustworthy a driver has been over recent trips.

The compatibility score that decorates each ride card on the search results is computed at the time of the search. It takes as input the geographic match (origin, destination), the shared history with the driver (number of past trips, average rating left), the alignment with the user's stated preferences (music, smoking tolerance, wifi), and the reliability of the driver. The four contributions are weighted and combined into a single percentage that the user can interpret at a glance.

\subsection{Sprint Review}

The review at the end of Sprint~3 was the longest of the four. The supervising engineer asked for a demonstration of the price pipeline with several combinations of student status and promo codes, which forced the team to walk through the order of operations on the whiteboard. One bug was caught during this exercise: when both the student discount and a promo code applied, the promo was being computed on the original price rather than on the price already reduced by the student discount, which slightly favored the passenger. The order of operations was fixed the same evening and a unit test was added to lock it for the future. The retrospective also flagged that the explainable nature of the recommendation rules had been a good choice: every recommendation could be justified to a driver who would ask for the reasoning, which would not have been possible with a learned model.

\subsection{Detailed Conception}

The chat feature was deliberately kept simple. Rather than introducing a WebSocket server, which would have added an operational dependency that the deployment plan does not yet cover, the conversations are polled every three seconds. This poll-based approach is sufficient for the volumes targeted by the project and remains within the limits of what the SQLite backend can sustain. Read receipts and date dividers are computed on the client to keep the API surface small. The complaint and rating workflows reuse the existing booking entities and only add their own tables, which kept their conception light.

The administration panel of Sprint~4 deserved more attention. Seven tabs were grouped under a single page, each backed by a dedicated handler on the backend, and each tab implements its own filters and actions. The challenge was less in the design of any individual tab than in the overall organization, since several actions trigger side effects that propagate to other parts of the system. The approval of an organizational account, for example, automatically grants the discount eligibility to all the email addresses registered under that organization.

\subsection{Sprint Review}

The review at the end of Sprint~4 was also the closing review of the project. All user stories of the sprint backlog were accepted. Two minor remarks were noted for the future: the polling interval of the chat could be made adaptive (a longer interval when the conversation is idle and a shorter one when a message has just been sent), and the right-to-left flipping of Arabic was missing on a single non-localized icon button, which was fixed during the review itself. The retrospective for the project as a whole highlighted three things the team would do differently next time: agreeing on the API error format on the very first day of Sprint~0 instead of letting it emerge sprint after sprint, writing the unit tests of the price pipeline before its implementation rather than after, and taking the screenshots of each screen as soon as it was finished, instead of producing them all at once before writing this report.

\section{Testing}

Testing was carried out continuously during the implementation phase, rather than left to a final stage.

\subsection{Unit Tests}

Unit tests were written for the most sensitive business rules of the backend: the computation of the total amount with the student discount and the promo code, the enforcement of the prepayment percentage, the validation of user inputs, and the state machine of the booking status. These tests catch regressions early and serve as a living documentation of the rules. The price pipeline test suite, in particular, includes the combination that revealed the bug found during the Sprint~3 review.

\subsection{Integration Tests}

Integration tests were performed through Postman collections that replay the main scenarios end to end: registration, login, trip creation, booking, payment, rating, and complaint. Each collection was executed after every significant change on the backend, and a short subset was kept in the repository as a smoke test that runs in less than a minute.

\subsection{Manual Testing}

Manual tests were conducted on the web application and on the mobile application, including cross-device testing on three Android phones with different screen sizes. Feedback from members of the host organization also helped detect usability issues that automated tests cannot catch, such as a confusing wording on the cancellation confirmation dialog that was rephrased the same week.

\section{Deployment}

The web application is deployed on the development environment provided by ATOMIC IT through XAMPP, with the backend mounted under \texttt{/forsadrive} on the local Apache instance. The mobile application is built with \texttt{flutter build apk} and distributed manually as a release APK. Production deployment was not part of the internship perimeter, but the path is straightforward: replacing SQLite with PostgreSQL or MySQL, hosting the backend behind HTTPS on a VPS, integrating a real payment provider such as Konnect or Paymee in place of the simulated wallet, and publishing the mobile application on the Google Play Store. The class diagram and the API surface have been kept stable enough that this migration would not require a structural change.

\section*{Conclusion}

This chapter closed the realization phase of ForsaDrive. Sprint~3 added the wallet and the intelligent layer that distinguishes a working prototype from a useful product: explicit financial information for the user, an explainable reliability score for drivers, an analytics dashboard, a promo code, and a compatibility score that helps the passenger pick a ride at a glance. Sprint~4 then completed the platform with the community features --- chat, ratings, complaints, social feed, HelpDesk --- and the multilingual interface, before the testing and deployment work brought the project to its current state. Together with the previous chapters, this discussion shows how a Tunisian carpooling platform can be built within the time of a final-year internship by following an agile process and by making technological choices that are deliberately aligned with both the local context and the available skills of the team.
